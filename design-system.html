03Components

Purpose, hierarchy, and state

Components share a small visual vocabulary. Their emphasis follows the consequence of the action, rather than the order they were added.

Actions

One primary action per decision. Use verb labels. Hover and focus remain visible; loading prevents duplicate submission. Reserve red for errors and consequential rejection.

Input & validation

Enter a domain only, such as myapp.com.

Labels remain visible. Show a specific correction next to the field and preserve what the user entered. Never validate with color alone.

Connection states

ConnectedAgent can request browser actions
PausedAccess temporarily stopped
UnpairedPairing is required

State labels always accompany indicators. Paused and unpaired are distinct conditions with different next steps. Avoid pulsing dots and vague “offline” labels.

Failure & recovery

Couldn’t connect to your agent.The local connection is unavailable. Check that your agent is running, then retry.
Agent connected. You’re ready to browse.

State the outcome first, then the next step. Keep recovery beside the failure. Announce success without forcing a dismissible modal.

04Behavior & voice

Trust is built in the details

Explain scope before consent.

Approval copy names the action, domain, and affected field. “Allow once” applies only to the current request. Persistent policy changes live in a separate section.

Make interruption reversible.

Pause preserves the connection and configuration. Resume returns to the same context. Disconnect is a separate action; never use “Disable” for both.

Keep technical detail useful.

Domains and CLI commands help developers act. Internal element IDs, raw exceptions, and instructions addressed to an agent belong in expandable diagnostics.

Respect a compact surface.

Use 14px body text, 12px supporting metadata, and 20px padding in a 390px popup. Reflow long domains and messages; preserve clear targets and keyboard order.

Reduce uncertainty, not just motion.

Never announce success before acknowledgement. Preserve input on failure. When no requests remain, explain that the queue is empty; an empty card is not a loading state.

Use a composed, direct voice.

“Agent connected.” “This request was denied.” Avoid hype, blame, and generic “Something went wrong” messages. No celebratory animation around permissions.

05Implementation reference

Intent that survives the handoff

Carry the reasons into the build.

This is a proposed revision of the supplied design reference. It does not update the extension’s popup or permission engine. Map the patterns to the real implementation before claiming parity.

  • Keep connection, pending approval, and site policies in that order.
  • Use shared semantic tokens; avoid one-off colors and arbitrary radii.
  • Implement focus, pending, failure, empty, and success states together.
  • Enforce consent scope in the backend; labels alone cannot limit access.
  • Keep a visible record of approval and policy outcomes.

Design review & validation notes

Observed in the supplied file: every section used nearly identical hierarchy; approval text exposed internal instructions; inputs lacked persistent labels; icon-only removal controls lacked accessible names; relative asset paths had no accompanying files.

Refined: task-based hierarchy, explicit one-request consent, labeled native controls, distinguishable connection states, persistent feedback, responsive structure, and an honest asset inventory.

Assumptions to validate: developers are the primary users; a 390px surface fits the target extension; sensitive actions require explicit approval even on allowed sites. Confirm these with the existing implementation and actual users.

Verified: HTML IDs, navigation anchors, error-description references, JavaScript syntax, and DOM simulations of pause/resume, allow once, deny, reset, pairing validation/loading/success, and domain validation. Calculated contrast for primary button text, muted text, attention, error, and success text exceeds 4.5:1. Browser installation failed, so rendered desktop/mobile layouts, zoom, focus movement, clipboard behavior and screen-reader output remain unverified. DOM simulations are not browser tests.

Production review still needed: real pairing, token handling, request payloads, server acknowledgement, permission enforcement, assistive technology behavior, and the actual extension context. This specimen does not validate those systems.
